# 多模态微调方案设计

本文先整理多模态模型微调的通用方法论，再说明本项目（桌面 GUI 智能体，基座 Qwen2.5-VL-3B）怎么落地、
跑哪些对照、用什么标准判定交付配方。数据与指标口径见《系统全面评估报告》。

## 一、方法论

### 1. 训练哪些部分：按优先级的冻结策略

多模态模型比纯文本模型多两个组件——视觉编码器（ViT）和对齐层（projection / merger），
微调时按下表决定解冻范围。

| 优先级 | 训练对象 | 触发条件 | 学习率 |
|---|---|---|---|
| 必训 | 对齐层 + 语言模型（LoRA 挂 q/k/v/o，可加 gate/up/down） | 默认 | 语言模型 5e-5~1e-4；对齐层约 2e-4 |
| 例外 | 只训语言模型 | 只想改回答风格，图片理解已足够 | 同上 |
| 低优先级 | 视觉编码器最后 1~4 个 block（从最后往前解冻） | 训了对齐层，图片特征仍提不出来 | 取语言模型的几分之一 |
| 按数据域 | 解冻更多 block | 数据与通用图像差距极大（工业、医学、UI、表格），或需要细粒度小目标、高分辨率细节 | 同上 |
| 按任务 | 额外的任务头 | 目标检测、分割、指代表达 | — |

学习率的两条规律：模型越大学习率越小；可训练参数越少学习率可越大（所以对齐层比语言模型高一档，
强化学习阶段降到 1e-6 量级）。

### 2. 训练流程：分阶段

1. **对齐预热**：只训对齐层，先把视觉特征映到语言空间。
2. **多模态指令微调**：对齐层 + 语言模型 LoRA 一起训。
3. **按需**：解冻视觉编码器后几层，或提高输入分辨率。
4. **偏好对齐**：DPO / RLHF，只训文本层，不动对齐层和视觉编码器。

数据量分档对应不同解冻计划：小于 10 万条走保守方案，10 万~100 万可放开更多，超过 100 万
（一般是视频、多图场景）才用最激进的方案。小场景约 4000~5000 条能得到不错的泛化，
训练集与测试集必须划分。

### 3. 数据构造

- 只用公开数据集的**图片**，不用它自带的标注；用当前最强的多模态模型按提示词重新标注，
  再加人工校验。微调一个小模型的意义在于它在特定领域比通用大模型更准更快，标注不校验就没有这个意义。
- 给数据打领域标签和细类标签，保证每类覆盖均衡，避免某一类特别多、某一类特别少。
- 规则过滤 + 模型过滤 + 去重；用奖励模型筛高质量问答对。
- 拒绝采样：生成带思维链的回答，与真值比较，留下好的做 SFT，被拒的正好拿去构造 DPO 数据。

### 4. 工程上与纯文本微调的差异

- Processor 负责把图片路径转成视觉 token 并与文本拼接，视觉部分夹在
  `vision_start` / `vision_end` 两个特殊 token 之间。
- 一个 batch 除 `input_ids` / `attention_mask` / `labels` 外，多出 `pixel_values`
  （图片数 × 通道 × 高 × 宽）和 `image_grid_thw`（怎么切块），用来算视觉 token 占多少位置、
  哪些位置要 mask 掉不计 loss。
- 挂 LoRA 只需写 `target_modules`；做全量微调要自己写 collator，并手动设 `requires_grad`。
- 推理时 LoRA 需与基座合并，全量微调直接从 checkpoint 加载。

## 二、本项目怎么落地

任务是在 1920×1080 桌面截图上判断下一步动作并点准控件，属于上表里「UI + 细粒度小目标 +
高分辨率细节」那一类，不是「只想改回答风格」。

### 1. 落在方法论的哪一档

方法论的三档里，本项目属于第二档「图能看懂，但领域理解不够」：

- 基座在 ScreenSpot 桌面 334 条上能认出控件，说明 ViT 的视觉特征是提得出来的，不是第三档；
- 但它把「该点哪个控件」转成坐标这一步不够准，图标尤其差，属于视觉—语言对齐不足；
- 同时输出必须是固定的 JSON 动作格式，这部分归第一档，靠语言模型 LoRA 解决。

所以方案是**对齐层全量训练 + 语言模型 LoRA**，ViT 全冻。对照实验支持这个选择：加训对齐层之后
流程内的点击精度是三组里最高的（见第五节）。

| 方法论 | 本项目 |
|---|---|
| 语言模型 LoRA 挂 q/k/v/o + gate/up/down | `--lora-targets all`，36 层共 252 个投影、29.9 M |
| 对齐层全量训练 | `--train-merger full`，36.71 M 参数全部可训 |
| 对齐层学习率更高 | `--merger-lr 2e-4`，语言模型仍用 1e-4 |
| ViT 后 1~4 block | 条件触发，见判定标准 Q3 |
| 数据用强模型标注 + 人工校验 | 动作与拆解样本用 ScreenAgent 官方标注；`finished` 样本官方数据里没有，用 25 个任务的终态程序化生成 |
| 划分训练 / 验证 | 按 session 切，两边无 session 重叠 |

### 2. Qwen2.5-VL-3B 的三块结构

| 组件 | 规模 | 本项目怎么处理 |
|---|---|---|
| ViT（视觉编码器） | 32 层，隐藏维 1280 | 全部冻结 |
| 对齐层 `visual.merger` | `mlp.0` 5120→5120、`mlp.2` 5120→2048，共 36.71 M | **全量训练**，学习率 2e-4 |
| 语言模型 | 36 层，`q/k/v/o_proj` + `gate/up/down_proj` | LoRA r=16，学习率 1e-4 |

对齐层把 ViT 输出的视觉特征转成语言模型能读的视觉 token：每 4 个图块特征拼成 5120 维，
过一层同维映射和激活，再压到语言模型的 2048 维。这一层就是「视觉信息能不能变成准确的语言理解」
的瓶颈所在。

工程上有一处要注意：全量训练对齐层时它不能被 4-bit 量化，否则权重是 uint8，PyTorch 会直接报
「only Tensors of floating point dtype can require gradients」。transformers 5.3.0 的跳过规则按
**线性层自己的名字**匹配，写模块路径 `"visual"` 或父模块名 `"merger"` 都不生效，必须写到叶子这一层
（`mlp.0` / `mlp.2`）。这样也只有对齐层留在 bf16，ViT 其余部分照样 4-bit，省显存。

### 3. 与方法论的取舍

| 取舍 | 原因 |
|---|---|
| 语言模型走 4-bit + LoRA | 12 GB 显存；对齐层单独保留 bf16 以便全量训练 |
| 不做「对齐预热」阶段 | 对齐层是预训练好的，直接进指令微调阶段 |
| 不做 DPO / RLHF | 输出是结构化动作，对错由动作类型和坐标判定 |

### 4. 数据这一侧的复核与结论

方法论里数据构造的权重最高，所以把训练数据从头查了一遍。ScreenAgent 官方 train 划分共
1082 步、182 个 session、753 张截图，实际能进两段式训练的只有 633 步：

| 去向 | 步数 | 占比 |
|---|---|---|
| 留：键盘类（hotkey 231 / type 195 / wait 63），不需要控件名 | 489 | 45% |
| 留：点击落在有文字的控件内，能写出控件名 | 144 | 13% |
| **丢：点击落在没有文字的位置（图标）** | **428** | **40%** |
| 丢：没有说明文字（`thought` 为空） | 21 | 2% |

两段式把位置写成控件名，图标没有文字就写不出名字，572 条点击类动作只收得到 144 条。
这解释了挂上权重后 ScreenSpot 图标准确率从 55.7% 掉到 47.9%：训练样本里的点击目标全是带文字的控件。

两条补救都不成立：放宽匹配到 `pad=0.02` 时，原本收得到的 152 条里有 21 条会改挑到别的元素，
把对的标签盖掉；数据集自带的 `thought` 是推理段落不是控件名，中位数 65 字、最长 938 字，且常含多个对象。

`reflections.jsonl` 897 行没有 `thought` 也没有对应截图，不可用。两段式的第二问（把控件名解析成坐标）
没有训练数据，定位能力完全来自基座。

已知局限：

- 428 条图标点击样本用不上。要用起来需要给每个图标生成一句描述并人工校验，本项目没有这个预算。
- 训练数据 579 条，低于经验值 4000~5000 条，提升幅度要按这个数据量读。

### 5. 训练计划：按验证损失 取最优，不训满

两次历史训练的验证损失 都在第 150 次更新后回升（1.13 -> 1.28、1.11 -> 1.23）：579 条数据配
29.9 M 可训练参数，约两轮就到最优。原来训满 6 轮且每次保存都覆盖同一路径，交付的是最后一步的
权重，也就是过拟合之后的。

现在每 50 次更新验证一次，只有验证损失创新低时才写交付路径；周期性存点另存一份，训练中断也不会丢。
这一条对结果的影响可能比解冻哪些层更大，和方法论「先少动参数、看效果、再逐步增加」是一个道理：
参数和轮数都不是越多越好。

## 三、实验矩阵

按方法论给的实验顺序做，全部在 Qwen2.5-VL-3B、`data/finetune_hist`（579 条：395 条动作 +
184 条拆解）、r=16、6 轮、语言模型 lr 1e-4、640 视觉 token、4-bit 上跑，除标出的一项外
超参完全一致。

| 编号 | ViT | 对齐层 | 语言模型 | 变量 | 状态 |
|---|---|---|---|---|---|
| Q0 | 冻结 | 冻结 | 不训 | 基线 | 已完成 |
| Q1 | 冻结 | 冻结 | LoRA | 对照 | 已完成 |
| Q2 | 冻结 | 全量，lr 2e-4 | LoRA | 对齐层 | 已完成，**交付配方** |
| Q3 | 最后 4 个 block，lr 取 1/5 | 全量 | LoRA | ViT | 未触发 |

## 四、判定标准

先定标准再看结果，避免事后挑数字。

**主指标**

- 定位：ScreenSpot 桌面 334 条的元素准确率，单独看图标子集 140 条（方法论里「细粒度小目标」指的就是它）
- 动作：ScreenAgent test 353 步的 Op.F1 macro

**次指标**：Step SR ≤0.10 / ≤0.14、无法执行率、单步耗时。

**噪声下限**：334 条上 1 个百分点约等于 3.3 条，353 步上 1 个百分点约等于 3.5 步。
两个配置差不到 1 个百分点，不做方向性结论。

**判定规则**

| 判定 | 规则 |
|---|---|
| Q1 是否有效 | Op.F1 macro 高于 Q0，说明动作决策和输出格式已经学到 |
| Q2 是否进交付配方 | 原定为「ScreenSpot 总体不低于 Q1」。跑完发现 ScreenSpot 与流程内定位给出相反结论，已改为按流程内的条件定位命中率判定，改动原委写在第五节 |
| Q3 是否开跑 | Q2 之后图标准确率仍低于基座，即对齐层解决不了「看不清小图标」 |
| 真机复测 | 交付配方定下来后跑 25 个任务评测集，`--max-steps 20`，按《系统全面评估报告》的安全流程 |

## 五、结果与判定

训练两组都在第 150 次更新达到验证损失最低（计划 435 步）：

| 配置 | 可训练参数 | 时长 | 峰值显存 | 最优步 | 最优验证损失 |
|---|---|---|---|---|---|
| Q1 只训语言模型 | 29.9 M | 109.1 分钟 | 6.17 GB | 150 | 1.1050 |
| Q2 加对齐层全量 | 29.9 M + 36.7 M | 113.6 分钟 | 6.27 GB | 150 | 1.1002 |

离线评测，全部同口径（键盘动作要求输入内容也对）：

| 指标 | Q0 基座 | Q1 只训语言模型 | Q2 加对齐层全量 |
|---|---|---|---|
| 离线任务成功（70 条每步都对） | 1/70 | 2/70 | 2/70 |
| Step SR ≤0.10 | 13.0% | 19.0% | **21.2%** |
| Step SR ≤0.14 | 13.6% | 21.0% | **23.5%** |
| ScreenSpot 总体 | **71.6%** | 70.7% | 61.7% |
| ScreenSpot 文本 / 图标 | 83.0% / 55.7% | 83.0% / 53.6% | 70.6% / 49.3% |
| Op.F1 macro | 10.7% | 24.5% | **25.6%** |
| Op.F1 micro | 28.0% | 39.7% | **40.2%** |
| 无法执行 | 2.0% | 2.0% | 2.0% |
| 每步耗时 | 3.69 s | 16.00 s | **9.31 s** |

逐类动作 F1 与测试集真值条数：

| 动作 | 真值条数 | Q0 基座 | Q1 只训语言模型 | Q2 加对齐层（交付） |
|---|---:|---:|---:|---:|
| click | 181 | 0.509 | 0.665 | 0.661 |
| hotkey | 69 | 0.000 | 0.113 | 0.155 |
| type | 65 | 0.136 | 0.181 | 0.121 |
| scroll | 14 | 0.000 | 0.250 | 0.111 |
| left_double | 14 | 0.105 | 0.355 | 0.542 |
| right_single | 8 | 0.000 | 0.154 | 0.200 |
| wait | 2 | 0.000 | 0.000 | 0.000 |

非点击类 6 类（172 步）的宏平均 F1：Q0 4.0%、Q1 17.5%、Q2 18.8%。提升几乎全部来自基座答不出的
类型——基座在 hotkey、scroll、right_single 上都是 0。两版微调在逐类上各有胜负：Q2 在 hotkey、
left_double、right_single 上更好，Q1 在 type 和 scroll 上更好，这两类分别只有 65 步和 14 步。

**判据被修正过，这里写清原委。** 第四节原来的主判据是 ScreenSpot 总体准确率不得低于对照组。
按这条，Q2 低 9.0 个百分点应当否决。但把步级成功率拆开之后发现这条判据测的不是要测的东西。

步级成功率 = 类型对 **且** 点得准，两者混在一起。只取「真值是坐标类动作、且模型类型判断正确」
的步，剩下的差异就只来自定位：

| 配置 | 这类步数 | 其中距离 ≤0.10 | 条件命中率 | 中位点击距离 |
|---|---:|---:|---:|---:|
| Q0 基座 | 91 | 38 | 41.8% | 0.230 |
| Q1 只训语言模型 | 118 | 45 | 38.1% | 0.192 |
| Q2 加对齐层全量 | 123 | 56 | **45.5%** | **0.127** |

在真实流程里 Q2 的定位是三组中最准的，也是唯一比基座更准的一组；Q1 的条件命中率反而低于基座。
ScreenSpot 掉的 9 个百分点没有传导到流程内的定位——它是单发元素定位、查询是短控件名，
与本项目「第一问产出控件描述、第二问解析坐标」的分布不同，属于域外代理指标。

所以改用流程内的定位度量作判据，结论随之反转：

| 指标 | 更好的一组 | 差距 |
|---|---|---|
| 离线任务成功 | 平 | 2/70 对 2/70 |
| 步级成功率 ≤0.10 / ≤0.14 | Q2 | +2.2 / +2.5 个百分点 |
| 流程内条件定位命中率 | Q2 | +7.4 个百分点 |
| 中位点击距离 | Q2 | 0.127 对 0.192 |
| Op.F1 macro / micro | Q2 | +1.1 / +0.5 个百分点 |
| 每步耗时 | Q2 | 9.31 s 对 16.00 s |
| ScreenSpot（域外） | Q1 | +9.0 个百分点 |

**交付配方是 Q2**：ViT 冻结、对齐层全量训练（学习率 2e-4）、语言模型 LoRA。

保留的风险：ScreenSpot 掉 9 个百分点是真实的域外退化信号，而 25 个任务的真机套件是 Windows
桌面程序，也不是 ScreenAgent 的分布，Q2 的优势能否带过去要靠真机复测验证。
Q3 的触发条件是 Q2 之后图标准确率仍低于基座（49.3% 对 55.7%，确实更低），但 Q3 要在 Q2 基础上
再解冻 ViT 后 4 个 block，属于下一轮的事。

**训练轮数的影响大于解冻范围。** Q1 的验证损失从第 150 步的 1.1050 一路升到第 400 步的 1.6232，
如果按原来固定训满 435 步，交付的会是后者。取最优步之后 ScreenSpot 是 70.7%、图标 53.6%，
基本回到基座水平（71.6% / 55.7%）。

**对齐层确实该训。** 579 条数据全量训练 36.7 M 参数没有过拟合到损害流程内定位的程度，反而是
三组里点得最准的一组。用 ScreenSpot 判断会得出相反结论，这提醒了一件事：选判据要选与部署路径
同分布的度量，域外基准只能当旁证。
