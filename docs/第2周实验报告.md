## 三、系统组成

**模型**：本地 Qwen2.5-VL-3B-Instruct，bf16，显存 7.0 GB。端到端每步平均 3.0 s，含截图、OCR、推理和动作执行。

**Agent 循环**：每步截图并 OCR，把任务、执行历史、带编号的元素清单组成提示词，模型返回 Thought 和 Action，执行后结果写回历史。模型用元素编号指定目标，由 Agent 查表换成归一化坐标；直接给坐标时，超出 0~1 的按其 `smart_resize` 尺寸换算。

**任务拆解与规划**（`gui_agent/planner.py`）：按 ScreenAgent 的 Planning-Acting-Reflecting 三段。Planning 把任务拆成子任务清单，Acting 针对当前子任务出动作，Reflecting 看执行后的屏幕判断子任务的状态，判定沿用 ScreenAgent 数据集里 `EvaluateSubTaskAction` 的三个取值：`sub_task_success` 推进到下一个、`need_retry` 保持当前子任务、`need_reformulate` 重新拆解（次数有上限）。拆解失败时退回单步循环。

`--plan` 打开，默认关闭：本文第四、五节的数字都是在单步循环上测的，规划的效果单独作为一组对照，放到下周和微调一起量。

**框架**：提示词用 LangChain 的 `PromptTemplate`，输出解析实现成 `BaseOutputParser`，两者与模型调用组成 Runnable 链（`gui_agent/chain.py`）。主干是本地 Qwen2.5-VL，每步送一张截图，不走 LangChain 的 ChatModel 接口，用 `RunnableLambda` 包成链上的一环。换成 API 后端时链不用改。

**终止条件**：任务完成、动作失败、连续 3 步重复同一动作、达到步数上限。

**安全**：默认 dry-run 只打印动作不执行；任务涉及的文件读写都在 `logs/scratch/`；锁屏类组合键和形似破坏性命令的输入直接拒绝；鼠标甩到屏幕角落触发 FAILSAFE 中断。

## 四、基础任务测试

五个任务各跑一次，`scripts/run_tasks.py --live`。

| 任务 | 结果 | 步数 | 耗时 |
|---|---|---|---|
| open_browser | 不通过 | 3 | 29.5 s |
| search_content | 不通过 | 4 | 24.2 s |
| open_file | 不通过 | 11 | 117.0 s |
| type_and_save | 不通过 | 12 | 116.8 s |
| close_app | 不通过 | 10 | 79.4 s |

**成功率 0/5**，共 40 步，平均每任务 73.4 s。原始数据 `logs/tasks_v1.2_noplan.json`。

验收由程序判断，比对执行前后的状态差异：新出现的浏览器进程加新增窗口、新增的窗口标题、文件内容、进程从有到无。

大纲的「发送消息」改成在记事本输入并保存到本地文件，验收看文件内容：真发消息不可逆且对外。

### 验收条件的一处更正

`open_browser` 起初只判「出现新的浏览器进程」。浏览器会持续起后台辅助进程（更新程序、渲染器），任何一个新 PID 都会让它通过——实测有一轮 Agent 只输出了一个 `call_user`、一次点击都没有，验收仍判通过。

改成新进程和新窗口两个条件都要满足后重测，成功率由 1/5 变为 0/5。上面的表和本报告其他成功率数字都是改判定之后重测的结果。

### 失败归因

40 步里双击 20 次、`type` 13 次、单击 3 次，另有 4 条 `call_user` 终止记录。

模型会用键盘。这与 ScreenAgent 测试划分上的单步评测一致：键盘动作召回 46.6%（第五节）。

失败集中在定位：点击距离中位数 0.318，点不中目标 → 界面不变 → 模型看到同一屏给出同一个动作 → 卡住检测中止。下周先解决定位。

## 五、v1.0 基线

### ScreenAgent 测试划分：动作生成

`scripts/eval_screenagent.py`，官方 test 划分全量 353 条、70 个 session。给模型截图和任务描述，让它输出下一步动作，与人工修正后的动作比。

| 指标 | 结果 |
|---|---|
| 动作类型准确率 | 149 / 353 = **42.2%** |
| 键盘动作召回 | 61 / 131 = **46.6%** |
| 点击距离中位数 | 0.318（归一化） |
| 距离 ≤ 0.10 | 45 / 177 = 25.4% |
| 解析失败 | 12 |

平均单条 4.93 s，原始数据 `logs/screenagent_base.json`。

主要混淆：`click→left_double` 33 次、`hotkey→type` 30 次、`type→click` 26 次。模型分得清要不要敲键盘，分不清是打字还是组合键。

点击距离中位 0.318，预测点离真值差了三分之一个屏幕。这是主要瓶颈，也解释了第四节里四个任务为什么都在早期被卡住检测中止。

### 任务拆解与规划的对照

同一套任务加 `--plan` 再跑一次，原始数据 `logs/tasks_v1.2_plan.json`。

| | 成功率 | 总步数 | 平均耗时 |
|---|---|---|---|
| 单步循环 | 0 / 5 | 40 | 73.4 s |
| 带规划 | 0 / 5 | 22 | 40.2 s |

成功率没有变化，步数和耗时降了近一半——规划让模型少做无效尝试，但没能把任务做成。

拆解本身是对的。`type_and_save` 拆成「打开记事本 → 输入你好 → 选择文件菜单 → 选择另存为 → 选择保存路径 → 点击保存按钮」，是可执行的正确步骤；执行时仍然点不到目标控件。

反思偏乐观：14 次判定里 12 次是 `sub_task_success`，而程序验收全部不通过。这一项目前只能用来推进子任务，不能拿来判定任务成败。

落地过程中修了四处，都是只有跑真机才暴露的：

| 现象 | 原因 |
|---|---|
| 五个任务一个子任务都没拆出来 | 模型回的是 `[{"action": "..."}]`，解析只收字符串数组 |
| 步数从 11/9/10 掉到 2/4/1 | 子任务走完就判定整条任务成功，等于让模型的自我判断决定成败 |
| 计划中途消失 | 重拆返回空时覆盖了原计划 |
| 四个任务拆出同一个无关计划 | 提示词里的格式示例是个裸数组，模型原样抄回 |

最后一条是提示词写法问题：示例必须写明属于另一个任务。ScreenAgent 的提示词是先说「我的任务是搜索麦田怪圈」再给拆解，本项目起初漏了这一层。

### ScreenSpot 桌面部分：元素定位

全量 334 条，判定标准是模型给出的点落在真值框内。

| 分组 | 命中 / 总数 | 准确率 |
|---|---|---|
| 总体 | 239 / 334 | **71.6%** |
| 文字类 | 161 / 194 | 83.0% |
| 图标类 | 78 / 140 | 55.7% |
| Windows | 112 / 162 | 69.1% |
| macOS | 127 / 172 | 73.8% |

平均单条 1.68 s，坐标解析失败 0 条。

文字类和图标类差 27 个百分点，与基础任务里的表现一致：模型倾向于在能读到文字的地方点击，遇到图标就开始试探。

这个 71.6% 和 ScreenAgent 的数字不可比：ScreenSpot 的指令直接给出目标控件（「点击保存按钮」），判定是点落在真值框内；ScreenAgent 给的是整条任务（「打开文件资源管理器」），判定是与真值点的距离。

### 小结

| 基线 | 数值 |
|---|---|
| 基础任务成功率 | 0 / 5 |
| 动作类型准确率（ScreenAgent test） | 42.2% |
| 键盘动作召回（ScreenAgent test） | 46.6% |
| 元素定位准确率（ScreenSpot 桌面部分） | 71.6% |
