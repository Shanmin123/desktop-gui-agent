## 三、系统组成

**模型**：本地 Qwen2.5-VL-3B-Instruct，bf16，显存 7.0 GB。端到端每步平均 5.0 s，含截图、OCR、推理和动作执行；同样的循环在 3840×2160 下是 9.2 s。

**Agent 循环**：每步截图并 OCR，把任务、执行历史、带编号的元素清单组成提示词，模型返回 Thought 和 Action，执行后结果写回历史。模型用元素编号指定目标，由 Agent 查表换成归一化坐标；直接给坐标时，超出 0~1 的按其 `smart_resize` 尺寸换算。

**任务拆解与规划**（`gui_agent/planner.py`）：按 ScreenAgent 的 Planning-Acting-Reflecting 三段。Planning 把任务拆成子任务清单，Acting 针对当前子任务出动作，Reflecting 看执行后的屏幕判断子任务的状态。

判定沿用 ScreenAgent 数据集里 `EvaluateSubTaskAction` 的三个取值：`sub_task_success` 推进到下一个子任务，`need_retry` 保持当前子任务，`need_reformulate` 重新拆解（次数有上限）。拆解失败时退回单步循环。

**两段式定位**（`--locate-target`）：第一段只让模型说要操作哪个控件，第二段用定位提示词把描述解析成坐标，绕开 OCR 元素编号。见第四节。

`--plan` 和 `--locate-target` 都默认关闭，第四节逐个开关做了对照。

**框架**：提示词用 LangChain 的 `PromptTemplate`，输出解析实现成 `BaseOutputParser`，两者与模型调用组成 Runnable 链（`gui_agent/chain.py`）。主干是本地 Qwen2.5-VL，每步送一张截图，不走 LangChain 的 ChatModel 接口，用 `RunnableLambda` 包成链上的一环。换成 API 后端时链不用改。

**终止条件**：任务完成、动作失败、连续 3 步重复同一动作、达到步数上限。

**安全**：默认 dry-run 只打印动作不执行；任务涉及的文件读写都在 `logs/scratch/`；锁屏类组合键和形似破坏性命令的输入直接拒绝；鼠标甩到屏幕角落触发 FAILSAFE 中断。

## 四、基础任务测试

运行分辨率 1280×720。屏幕原生是 3840×2160，但 Qwen2.5-VL 的像素预算是
1,003,520，`smart_resize` 会把 4K 压到 1316×728，丢掉 88% 的像素；1280×720 是
0.92 MP，算出 1288×728，等于不缩放，模型看到的就是屏幕上的像素。

`scripts/run_tasks.py --live --resolution 1280x720`，跑完自动切回原分辨率。

| 任务 | 结果 | 步数 | 耗时 |
|---|---|---|---|
| open_browser | 不通过 | 1 | 12.0 s |
| search_content | 不通过 | 6 | 19.7 s |
| open_file | 不通过 | 4 | 21.9 s |
| type_and_save | 不通过 | 12 | 62.4 s |
| close_app | 不通过 | 1 | 4.0 s |

**成功率 0/5**，共 24 步，平均每任务 24.0 s。原始数据 `logs/tasks_v2_720_noplan.json`。

验收由程序判断，比对执行前后的状态差异：新出现的浏览器进程加新增窗口、新增的窗口标题、文件内容、指定进程从有到无。

大纲的「发送消息」改成在记事本输入并保存到本地文件，验收看文件内容：真发消息不可逆且对外。

### 五组对照

| 配置 | 成功率 | 总步数 | 平均耗时 |
|---|---|---|---|
| 3840×2160 单步循环 | 0 / 5 | 40 | 73.4 s |
| 3840×2160 带规划 | 0 / 5 | 22 | 40.2 s |
| 1280×720 单步循环 | 0 / 5 | 24 | 24.0 s |
| 1280×720 带规划 | 1 / 5 | 45 | 45.2 s |
| 1280×720 两段式定位 | **2 / 5** | 40 | 63.9 s |

分辨率：同为单步循环，从 3840×2160 换到 1280×720 后每任务耗时从 73.4 s 降到 24.0 s，每步从 9.2 s 降到 5.0 s。成功率没变，省的是时间。

两段式定位通过了 `open_browser` 和 `close_app`。`close_app` 连续点在 (1251, 16)——记事本窗口右上角的关闭按钮，setup 启动的那个进程确实被关掉。它为什么更准，见「定位为什么不准」一节。

每个配置只跑一次、每次 5 个任务，成功率之间差的是一两个任务，单看这张表说明不了问题。下一节的离线对照样本量更大，结论更可靠。

### 验收条件的一处更正

`open_browser` 起初只判「出现新的浏览器进程」。浏览器会持续起后台辅助进程（更新程序、渲染器），任何一个新 PID 都会让它通过——实测有一轮 Agent 只输出了一个 `call_user`、一次点击都没有，验收仍判通过。

改成新进程和新窗口两个条件都要满足后重测，最早那次 1/5 变为 0/5。本报告所有成功率都是改判定之后重测的。

### 定位为什么不准

同一批 120 条 ScreenSpot 桌面样本、同一个模型，只换「怎么问模型要位置」：

| 问法 | 命中率 |
|---|---|
| 直接问坐标，已经告诉它要找哪个控件 | 70.0% |
| 当前 Agent 提示词，给 OCR 元素清单 | 40.8% |
| 两段式：先问要操作哪个控件，再定位 | **62.5%** |

差距的来源：当前提示词下模型 111/120 次用 OCR 元素编号指位置，几乎不给坐标。而 OCR 只认文字，图标和无标签按钮没有编号可指，模型就随手编一个——实测出现过 `element: 783` 这种当前屏幕上根本不存在的编号。

这也解释了第五节里图标类 55.7% 和文字类 83.0% 的 27 个百分点差距：有文字的控件 OCR 能给出编号，图标不能。

两段式把「点什么」和「点哪」拆开。第一段只让模型回 `{"action": {"type": "click", "target": "关闭按钮"}}`，第二段用定位提示词把描述解析成坐标——那条路径已知有 70% 的上限。不依赖 OCR 能否读出文字，所以图标也能指。

`--locate-target` 打开，默认关闭。

### 失败归因

模型会用键盘，五组里 `type` 和 `hotkey` 都出现过。这与 ScreenAgent 测试划分上的单步评测一致，键盘动作召回 46.6%（第五节）。

失败集中在定位。点击距离中位数 0.318，点不中目标 → 界面不变 → 模型看到同一屏给出同一个动作 → 卡住检测中止。降低分辨率只缩短了耗时；两段式定位把命中率从 40.8% 提到 62.5%，但离 70% 的上限还有距离，下周微调继续冲这一项。

### 任务拆解与规划

`gui_agent/planner.py`，按 ScreenAgent 的三段。拆解本身是对的，`type_and_save` 拆成「打开记事本 → 输入你好 → 选择文件菜单 → 选择另存为 → 选择保存路径 → 点击保存按钮」，是可执行的正确步骤；执行时仍然点不到目标控件。

反思偏乐观：1280×720 带规划这一轮 19 次判定里 18 次是 `sub_task_success`，而只有 1 个任务真的通过。这一项目前只能用来推进子任务，不能拿来判定任务成败。

跑真机时发现两点，都与提示词有关：

模型不按要求的格式回。提示词要字符串数组，它回的是 `[{"action": "..."}]`，解析要两种都认。这与第 1 周发现它输出 `left_click` 而非 `click` 是同一类问题。

格式示例会被原样抄回。示例最初是个裸数组，结果五个任务里四个拆出了示例里的那两条子任务，包括「关闭记事本」被拆成「点击文件资源管理器图标」。示例必须写明属于另一个任务——ScreenAgent 的提示词是先说「我的任务是搜索麦田怪圈」再给拆解。

## 五、v1.0 基线

### ScreenAgent 测试划分：动作生成

`scripts/eval_screenagent.py`，官方 test 划分全量 353 条、70 个 session。给模型截图和任务描述，让它输出下一步动作，与人工修正后的动作比。

| 指标 | 结果 |
|---|---|
| 动作类型准确率 | 149 / 353 = **42.2%** |
| 键盘动作召回 | 61 / 131 = **46.6%** |
| 点击距离中位数 | 0.318（归一化） |
| 距离 ≤ 0.10 | 45 / 177 = 25.4% |
| 解析失败 | 12 |

平均单条 4.93 s，原始数据 `logs/screenagent_base.json`。

主要混淆：`click→left_double` 33 次、`hotkey→type` 30 次、`type→click` 26 次。模型分得清要不要敲键盘，分不清是打字还是组合键。

点击距离中位 0.318，预测点离真值差了三分之一个屏幕。这是主要瓶颈，也解释了第四节里任务为什么大多在早期中止。

### ScreenSpot 桌面部分：元素定位

全量 334 条，判定标准是模型给出的点落在真值框内。

| 分组 | 命中 / 总数 | 准确率 |
|---|---|---|
| 总体 | 239 / 334 | **71.6%** |
| 文字类 | 161 / 194 | 83.0% |
| 图标类 | 78 / 140 | 55.7% |
| Windows | 112 / 162 | 69.1% |
| macOS | 127 / 172 | 73.8% |

平均单条 1.68 s，坐标解析失败 0 条。

文字类和图标类差 27 个百分点，与基础任务里的表现一致：模型倾向于在能读到文字的地方点击，遇到图标就开始试探。

这个 71.6% 和 ScreenAgent 的数字不可比：ScreenSpot 的指令直接给出目标控件（「点击保存按钮」），判定是点落在真值框内；ScreenAgent 给的是整条任务（「打开文件资源管理器」），判定是与真值点的距离。

### 小结

| 基线 | 数值 |
|---|---|
| 基础任务成功率（1280×720 单步循环） | 0 / 5 |
| 基础任务成功率（1280×720 两段式定位） | 2 / 5 |
| 动作类型准确率（ScreenAgent test） | 42.2% |
| 键盘动作召回（ScreenAgent test） | 46.6% |
| 元素定位准确率（ScreenSpot 桌面部分） | 71.6% |
