## Python 环境

用 Anaconda base 环境（Python 3.10.9），没有新建虚拟环境。原因是 base 里已经装好 torch 2.6.0+cu124，新建环境要重新下载约 2.5GB 的 CUDA 版 torch。

代价是 base 与其他项目共用，装包时容易互相影响。如果后面冲突变多，再迁到独立环境。

## 安装

```bash
pip install -r requirements.txt
python scripts/check_env.py          # 快速检查
python scripts/check_env.py --ocr    # 额外实测 OCR，首次会下载模型权重
```

## 实测结果

`python scripts/check_env.py --ocr`，19 项全部通过。

| 项 | 结果 |
|---|---|
| Python | 3.10.9 |
| PyTorch | 2.6.0+cu124，CUDA 可用 |
| CUDA 实算 | 2048×2048 矩阵乘 118.8 ms |
| 显存 | 12.0GB，空闲 10.8GB |
| mss 截图 | 3840×2160，平均 75.1 ms/帧 |
| pyautogui | 报告屏幕尺寸 3840×2160 |
| 坐标系 | 截图尺寸与控制尺寸一致 |
| easyocr 实测 | 全屏识别出 285 处文字，耗时 9.7s（含模型首次加载，见下面结论 2） |
| 其余库 | pynput、OpenCV 4.10、transformers 5.3.0、peft、accelerate、bitsandbytes、datasets、langchain、matplotlib、paddleocr 均正常 |

两点结论：

**1. 坐标系不需要换算。** 之前用 ctypes 在 DPI 不感知的情况下测，系统报告的屏幕是 2194×1234，与截图的 3840×2160 差 1.75 倍。但实际装好 pyautogui 0.9.54 后，它报告的就是 3840×2160，与 mss 一致，不存在偏移。感知模块内部仍然用 0 到 1 的相对坐标，但那是为了适配模型输入尺寸，不是为了修 DPI。

**2. 上面那个 9.7 秒是模型首次加载，不是稳态。** 这一条更正 8/24 当天的判断。

8/27 用 `scripts/bench_perception.py` 单独实测，把模型加载排除在计时之外，跑了四轮（每轮屏幕内容不同）：

| 轮次 | 截图 | 缩放 | OCR 原图 | OCR 缩放图 | 原图识别数 | 缩放图识别数 | 说明 |
|---|---|---|---|---|---|---|---|
| 1 | 62.7 ms | — | 1.42 s | 1.29 s | 27 | 3 | 缩放耗时把未预热的首次调用算进了平均，作废 |
| 2 | 107.4 ms | 3.5 ms | 1.68 s | 1.40 s | 31 | 3 | OCR 第一轮吃了 CUDA 初始化，缩放图那一列偏高 |
| 3 | 96.9 ms | 3.4 ms | 2.18 s | 1.97 s | 59 | 27 | 同上 |
| 4 | 90.2 ms | 3.2 ms | **2.43 s** | **1.55 s** | **65** | **22** | 已正确预热，以这一轮为准 |

每轮屏幕内容不同，识别数之间不可横向比较，但同一轮内原图与缩放图是同一张截图，可比。

三个结论：

- 8/24 记的 9.7 秒，绝大部分是 easyocr 第一次调用的初始化开销，整个 Agent 循环只付一次，稳态是 1.5 到 2.5 秒。当天据此得出的「全屏 OCR 太慢不能每步跑」不成立。
- **缩放确实能给 OCR 提速，但要付出精度代价**。第 4 轮（正确预热后）省 0.88 秒，识别到的文字从 65 掉到 22，少了三分之二。第 2、3 轮只差 0.2 秒是测量偏差：`p.reader` 只加载权重，第一次真正推理还带 CUDA 上下文初始化，这笔开销全记在了先测的缩放图那一轮头上。修正办法是先空跑一次 OCR 再计时。
  
  即便如此仍然选择在原图上跑：Agent 要靠元素位置去点，丢掉三分之二的文字比多花 0.9 秒严重得多。缩放只服务于模型的输入限制。
- 缩放本身很便宜，3 ms 左右。截图 60 到 110 ms 才是目前最大的固定开销。

第 6 周第 3 项「优化屏幕感知模块，提升 UI 元素识别的准确率与速度」可以从这里入手：只对发生变化的区域重跑 OCR，既保住原图精度又省掉大部分时间。
