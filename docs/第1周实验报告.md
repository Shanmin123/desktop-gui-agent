## 四、本周的五个问题

**1. cv2 在中文路径下存图静默失败**

项目目录名是中文，`cv2.imwrite` 按 ANSI 代码页处理路径，返回 False 但不抛异常，文件没写出来。脚本打印了"已存到"，目录里却是空的。`cv2.imread` 同理。改成 `imencode` 加 Python 文件接口，全项目统一走 `perception.imwrite` / `imread`。

**2. OCR 不能在缩放图上跑**

原本设计成缩放后再 OCR，以为能顺带提速。实测原图 2.43 秒识别 65 处，缩放图 1.55 秒只剩 22 处。easyocr 检测阶段内部本来就把长边压到 2560，再往下缩就低于它的工作分辨率。省 0.88 秒不值丢三分之二的文字，改成缩放只用于模型输入，OCR 走原图。

**3. pyautogui 打不出中文**

`KEYBOARD_KEYS` 里全是 ASCII，`write()` 对中文直接忽略。按 `text.isascii()` 分流，含中文的走剪贴板加 Ctrl+V。ScreenAgent 也是这个解法。

**4. 文本黑名单会误伤正常输入**

安全拦截最初写成子串匹配，`"format "` 把 `format the paragraph` 也拦了。改成锚定开头的正则。更根本的问题是同一段文字打进 Word 无害、打进 cmd 危险，光看文本判断不了上下文，所以这道防线只能挡最明显的情况，真正的保障是 dry-run、FAILSAFE 和虚拟机。

**5. 坐标校准一度测出 623 px 误差**

排查后是外部干扰：有别的程序在同时移动光标。单独跑纯移动测试，SetCursorPos、pyautogui duration=0、duration=0.1 三种方式在 15 个点上都是零误差。校准脚本加了重试和干扰检测，不再把干扰误报成缩放系数问题。

另外环境里 transformers 5.3.0 与 huggingface-hub 0.33.1 本来就不兼容，装依赖时顺带修了；easyocr 会把 numpy 顶到 2.x，导致 OCR 和其他项目一起挂，已钉回 1.26.4。

### 已提前完成的部分（8/31 - 9/2 的三项）

**数据集**：大纲点名的三个都不能直接用。ScreenAgent 在 HuggingFace 上没有、GitHub 仓库页也没给下载链接；WebArena 是 docker 网站环境不是数据集；Mind2Web 是 6.4 GB 的 HTML DOM 数据不含截图，带截图的版本 12.9 GB，且都是 Web 域。

改用两个约 1 GB 的桌面 grounding 数据集：`rootsautomation/ScreenSpot` 的桌面分片 334 条作评测集，`showlab/ShowUI-desktop` 7496 条作训练集（划分为训练 6747、验证 749）。两者的 bbox 都是归一化 `[x1,y1,x2,y2]`，与第 1 周定的数据格式一致，不需要转换，已抽样把框画回原图人工核对过。详见 `docs/数据集说明.md`。

**主干模型**：大纲清单里三个的实际情况是，Qwen-VL-Chat（18 GB）和 GLM-4V-9B（25.9 GB）的自定义建模代码是按 transformers 4.3x 写的，当前环境是 5.3.0；Llama-3.2-11B-Vision（19.9 GB）在 HuggingFace 上是 gated=manual，要先申请许可。改用同系列的当代版本 **Qwen2.5-VL-3B-Instruct**（7 GB），bf16 在 12 GB 显存上直接装得下。7B 版本需要 4bit，接口里留了开关。

**本地推理已跑通**：显存占用 6.99 GB，单条推理 2.62 秒。

**定位精度初步测量**：在 ScreenSpot 桌面分片上抽 20 条，命中率 60%（文字类 75%，图标类 50%），坐标解析失败 0 条。全量 334 条的正式基线还没跑完。

这个数字先确认了一件事：Qwen2.5-VL 输出的坐标不在原图像素空间，而在它内部 smart_resize 之后的空间（本机 3840×2160 会被压成 1316×728）。归一化除以原图尺寸会整体偏，命中率会接近 0，现在是 60%，说明坐标换算是对的。

看失败样本，错的基本都是无文字标签的图标：一个是在最小化和最大化两个按钮之间认错（差 46 像素），一个是把快速访问栏的保存图标找成了功能区按钮。这和分组数据对得上，也指出第 3 周微调该往图标类样本上偏。
