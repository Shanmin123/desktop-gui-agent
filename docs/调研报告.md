# GUI 智能体技术调研报告

对应大纲第 1 周第 1、2、3 项。最后更新 2026-08-26。

阅读目标是定下后面开发要用的五项选择：屏幕内容怎么送模型、动作用什么格式、怎么做任务规划、用哪个主干模型、评估怎么做。结论在第五节。

## 一、UI-TARS

来源：[arXiv:2501.12326](https://arxiv.org/abs/2501.12326)

### 1. 定位

端到端的原生 GUI 智能体模型，只接收截图作为输入，直接输出鼠标键盘操作，不依赖外部框架去包装商用模型。论文对比的是"用 GPT-4o 加人工提示词和工作流"这类方案，结论是端到端模型更好。

OSWorld 上 50 步得分 24.6、15 步 22.7，对应 Claude 的 22.0 和 14.9；AndroidWorld 46.6，对应 GPT-4o 的 34.5。

### 2. 统一动作空间（Table 1）

跨平台通用：

| 动作 | 说明 |
|---|---|
| `Click(x, y)` | 点击 |
| `Drag(x1, y1, x2, y2)` | 从一点拖到另一点 |
| `Scroll(x, y, direction)` | 在指定位置滚动 |
| `Type(content)` | 输入文本 |
| `Wait()` | 短暂等待 |
| `Finished()` | 任务完成 |
| `CallUser()` | 请求人工介入 |

仅桌面端：`Hotkey(key)`、`LeftDouble(x, y)`、`RightSingle(x, y)`。
仅移动端：`LongPress`、`PressBack`、`PressHome`、`PressEnter`。

**坐标用相对值，按屏幕尺寸归一化**，论文的说法是这样能在不同分辨率的设备之间保持一致。

### 3. 屏幕感知

只用截图，论文里没有提 OCR、也没有提无障碍树。

### 4. 输出格式

每一步同时输出 Thought 和 Action，一条轨迹写成 `(instruction, (o₁,t₁,a₁), (o₂,t₂,a₂), …, (oₙ,tₙ,aₙ))`，其中 o 是观察、t 是推理、a 是动作。

### 5. 四项主要工作

1. 增强感知：用大规模 GUI 截图数据集训练对 UI 元素的理解和描述。
2. 统一动作建模：把动作标准化成一个跨平台的空间，用大规模操作轨迹训练定位和交互。
3. System-2 推理：在多步决策中加入任务拆解、反思、里程碑识别等推理模式。
4. 反思式在线轨迹迭代训练：在数百台虚拟机上自动采集、过滤、修正新轨迹，让模型从自己的错误里学。

## 二、Claude Computer Use

来源：[官方文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)

### 1. 动作列表

一共 17 个：

- 截图类：`screenshot`、`zoom(region)`
- 鼠标点击：`left_click`、`right_click`、`middle_click`、`double_click`、`triple_click`，参数是 `coordinate` 和可选的修饰键 `text`（shift / ctrl / alt / super）
- 鼠标其他：`left_click_drag(start_coordinate, coordinate)`、`mouse_move`、`left_mouse_down`、`left_mouse_up`、`cursor_position`
- 滚动：`scroll(scroll_direction, scroll_amount, coordinate)`
- 键盘：`type(text)`、`key(text, repeat)`、`hold_key(text, duration)`
- 等待：`wait(duration)`

### 2. 坐标系

坐标是**截图的像素坐标**，原点在左上角，不归一化。`zoom` 之后模型给出的坐标仍然是整屏坐标系里的，不是放大图里的。如果自己把截图缩小了送模型，拿到坐标要按比例放大回去再执行。

这一点和 UI-TARS 相反：UI-TARS 用归一化相对坐标，Claude 用绝对像素坐标加外部换算。

### 3. 分辨率限制

推荐的桌面分辨率是 1024×768 或 1280×720，不建议超过 1920×1080。API 对图片有硬限制，超了会报错：

| 模型 | 长边上限 | 总像素上限 |
|---|---|---|
| Opus 4.7+ | 2576 px | 约 3.75 MP |
| 更早的模型 | 1568 px | 约 1.15 MP |

缩放系数取三者最小值：`1.0`、`长边上限/长边`、`sqrt(总像素上限/总像素)`。

### 4. 提高点击准确率的做法

- 提示词里把文字说明放在截图**前面**，能提升点击准确率。
- 小目标或者缩得太狠的截图，用 `zoom` 对局部再看一次全分辨率。

## 三、ScreenAgent

来源：[GitHub](https://github.com/niuzaisheng/ScreenAgent)、[arXiv:2402.07945](https://arxiv.org/abs/2402.07945)

### 1. 控制流程

Planning-Acting-Reflecting 三段循环：

- **Planning**：把用户任务拆成子任务。
- **Acting**：看截图，输出鼠标键盘动作，由控制器执行。
- **Reflecting**：看执行结果，决定继续、重试还是调整计划。

控制器按提示词模板拼出完整 prompt，连同截图一起发给模型。

### 2. 动作空间

参照 VNC 协议定义最基础的鼠标键盘操作，不用应用专有的 API，这样跨平台通用。大部分点击操作要求模型给出准确的屏幕坐标。键盘输入除 ASCII 外，中文等 Unicode 走剪贴板。

### 3. 数据集格式

```
session_id/
├── images/
│   └── <timestamp>.jpg
└── <timestamp>.json
```

JSON 的字段：`session_id`、`task_prompt`（另有 `_en` / `_zh` 两个语言版本）、`send_prompt`（同样有 en/zh）、`LLM_response`、`LLM_response_editer`、`video_height`、`video_width`、`saved_image_name`、`actions`。

两个细节值得借鉴：一是每条样本都记下截图当时的分辨率；二是模型原始输出 `LLM_response` 和人工修正后的 `LLM_response_editer` 分开存，`actions` 是从修正版解析出来的，也就是说训练用的是修正版。

### 4. 桌面控制方式

用 VNC 协议，控制器是 PyQt5 写的，连 VNC Server 取截图、发鼠标键盘指令，另有一个剪贴板服务（端口 8001）处理 Unicode 和长文本输入。

### 5. 支持的模型

GPT-4V（走 API）、LLaVA-1.5、CogAgent，以及在 CogAgent 基础上训练的 ScreenAgent 本身。在 `config.yml` 的 `llm_api` 段里选一个。

## 四、三者对比

| | UI-TARS | Claude Computer Use | ScreenAgent |
|---|---|---|---|
| 形态 | 端到端模型，专门训练 | 通用模型 + 工具接口 | 框架 + 可换模型 |
| 感知 | 只看截图 | 截图，可 `zoom` 局部 | 截图 + 提示词模板 |
| 坐标 | 归一化相对坐标 | 截图像素坐标，换算交给调用方 | 屏幕绝对坐标 |
| 动作数 | 桌面 10 个 | 17 个 | VNC 基础操作 |
| 规划 | 模型自带 Thought | 靠提示词 | Planning-Acting-Reflecting |
| 控制 | — | 调用方实现 | VNC + PyQt5 |

## 五、五项选择

**1. 屏幕内容怎么送模型**

以缩放后的截图为主，附带 OCR 识别出的元素列表作为文字补充。三个系统都不用无障碍树，本项目也不用。

本机 3840×2160 是 8.3 MP，远超模型输入限制，必须缩放。按 Claude 文档的算法，参照 1568 px / 1.15 MP 这一档，系数取 `min(1568/3840, sqrt(1150000/8294400)) = min(0.408, 0.372) = 0.372`，缩放后 1430×804。

**缩放只用于模型输入，OCR 在原图上跑。** 8/27 实测（见 `docs/环境配置文档.md`）：同一张截图，原图 2.43 秒识别出 65 处文字，缩到 1430×804 是 1.55 秒但只剩 22 处。原因是 easyocr 检测阶段内部本来就会把长边压到 2560，再往下缩就低于它的工作分辨率了。省下的 0.88 秒不值丢掉三分之二的文字，Agent 要靠元素位置去点。

两边坐标都归一化，所以原图识别出的元素框画到缩放图上仍然对齐，已用带框截图人工核对过。

定位不准时按 Claude 的 `zoom` 思路对局部再看一次全分辨率。

**2. 动作用什么格式**

用 UI-TARS 的桌面子集，10 个动作：`click`、`left_double`、`right_single`、`drag`、`scroll`、`type`、`hotkey`、`wait`、`finished`、`call_user`，坐标归一化到 0~1。第 3 周用公开数据微调时格式对齐，可以少一层转换。

已实现在 `gui_agent/schema.py`，附 16 项单元测试。

**3. 怎么做任务规划**

用 ScreenAgent 的 Planning-Acting-Reflecting 三段。大纲第 3 周要"实现简单的任务拆解与规划"、第 6 周要"错误检测与自动重试机制"，正好对应这三段。同时按 UI-TARS 的做法，每步先让模型输出 Thought 再输出 Action，理由存进执行记录，供后面分析失败原因和构造微调数据。

**4. 用哪个主干模型**

9/2 接入时查了大纲清单里三个的实际情况：

| 模型 | 权重大小 | 情况 |
|---|---|---|
| Qwen-VL-Chat | 18 GB | 2023 年发布，自定义建模代码是按 transformers 4.3x 写的，当前环境是 5.3.0 |
| GLM-4V-9B | 25.9 GB | 同上 |
| Llama-3.2-11B-Vision-Instruct | 19.9 GB | HuggingFace 上是 `gated=manual`，要先申请许可才能下载 |

三个都不能直接跑：前两个即使 4bit 量化装得下，建模代码大概率和当前 transformers 不兼容；第三个下不下来。

改用 **Qwen2.5-VL-3B-Instruct**（7 GB），是 Qwen-VL 的当代版本，同一个系列。bf16 在 12GB 显存上直接装得下，不需要量化。7B 版本 15.4 GB，需要 4bit，接口里留了 `load_in_4bit=True` 的开关。

**坐标空间要注意**：Qwen2.5-VL 输出的坐标不在原图像素空间，而在它内部 `smart_resize` 之后的空间。实测这台机器上 3840×2160 会被压成 1316×728，ScreenSpot 的 960×540 会变成 952×532。归一化必须除以 resize 后的尺寸，除以原图尺寸会整体偏。`gui_agent/models.py` 里用同一个 `smart_resize` 算这个尺寸，并用 ScreenSpot 的真值验证。

**5. 评估怎么做**

大纲第 7 周要 20 个任务、统计任务成功率和平均执行时间、错误率。每个任务配一个能用程序判断的成功条件（文件是否生成、窗口标题是否正确、进程是否启动），不靠人工看结果。

借鉴 ScreenAgent 的做法，执行记录里模型原始输出和实际执行结果分开存，这样既能算成功率，也能直接拿去做微调数据。这部分已经在 `Trajectory` 里实现。
